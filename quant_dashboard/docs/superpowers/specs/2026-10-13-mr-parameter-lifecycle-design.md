# 均值回归参数过期治理设计

日期：2026-10-13

## 1. 背景与问题

当前均值回归（MR）参数存在三套互相分叉的来源：

- 生产引擎实际读取 `config/strategy_runtime.json`，当前 revision 为 4，MR 的 `next_optimize_after` 为 2026-09-26。
- 策略健康审计读取旧产物 `mr_optimization_results.json`，其 `generated_at` 为 2026-07-28，当前质量折算年龄约 80 天。
- 回测页面在 `static/js/backtest.js` 内维护另一套硬编码默认值和三态预设。

现有优化器虽然可以再次运行，但其固定验证区间最晚只到 2026-03-27。直接重跑会重新写入当前时间，却不会引入新的样本外证据，因此不能被视为科学的参数续期。

## 2. 决策原则

采用“重验证优先、失败关闭、单一生产源”的治理方式：

1. 不允许仅修改时间戳或 `next_optimize_after` 来消除过期状态。
2. 以 `config/strategy_runtime.json` 作为唯一生产参数源。
3. 将 2026-03-28 至本地行情最新交易日作为冻结样本外区间；本次可用数据截至 2026-10-12。
4. 当前参数和候选参数均需在相同成本、相同标的池、相同 Regime 判定下比较。
5. 只有绝对质量门通过且相对表现不劣于当前参数时，候选参数才能发布。
6. 当前参数通过重验证但候选没有显著改善时，允许“参数不变、验证续期”。
7. 当前活跃 Regime 的参数若过期且重验证失败或证据不足，禁止新增买入；卖出、减仓和止损必须继续执行。

## 3. 方案比较

### 方案 A：重跑旧优化器并刷新日期

优点是改动少、耗时短。缺点是验证数据没有更新，会把旧证据包装成新证据，存在明显的模型治理问题，因此拒绝。

### 方案 B：只阻断过期参数

安全性较高，但策略会长期停用，且审计、生产、前端的来源分叉仍然存在，只适合作为临时降级，不作为最终方案。

### 方案 C：样本外重验证 + 质量门发布 + 失败关闭

能够区分“参数数值仍有效”和“确实需要换参”，同时保留可回滚证据。改动面较大，但符合投资模型的生产治理要求，选用此方案。

## 4. 参数生命周期模型

在运行时配置的 `strategies.mr` 下增加生命周期信息，按 Regime 独立记录：

```json
{
  "lifecycle": {
    "BEAR": {
      "status": "validated|stale|rejected|insufficient_evidence",
      "validated_at": "ISO-8601 timestamp or null",
      "data_through": "YYYY-MM-DD or null",
      "validation_run_id": "string or null",
      "next_validate_after": "YYYY-MM-DD or null"
    }
  }
}
```

规则：

- `validated`：最近一次冻结样本外验证通过，且未超过有效期。
- `stale`：超过 `next_validate_after`。
- `rejected`：当前参数在最新样本外验证中未通过绝对质量门。
- `insufficient_evidence`：活跃样本、交易次数或覆盖率不足，不能得出续期结论。
- 缺失或无法解析生命周期信息时按不可用处理，不回退为“默认新鲜”。

`published_at` 只表示配置文件发生过发布，不再被用作 MR 参数验证时间；行业或其他策略的发布不能顺带刷新 MR 新鲜度。

## 5. 重验证流程

### 5.1 数据边界

- 候选生成仍只允许使用截至 2026-03-27 的既有训练和验证数据。
- 冻结样本外区间固定从 2026-03-28 开始，结束于本地行情共同可用的最新交易日。
- 运行记录必须保存 `oos_start`、`data_through`、标的覆盖率和成本假设。
- 若最新行情距离当前预期交易日超过允许的数据滞后，则整个验证运行失败，不得续期。

### 5.2 无前视 Regime 判定

逐日 Regime 只能使用当日及之前的沪深 300 数据，复用生产引擎的状态判定规则。禁止用完整样本的未来信息反向标注历史状态。

### 5.3 对照组

同一冻结样本外区间运行两组：

- incumbent：当前 `strategy_runtime.json` 中的生产参数；
- challenger：既有优化器从训练区间产生的候选参数。

两组必须使用相同标的池、复权口径、手续费、滑点、仓位上限和信号延迟。

### 5.4 质量门

每个 Regime 至少检查：

- 最低有效交易次数；
- 最低信号覆盖率；
- Sharpe、Calmar 和最大回撤绝对门槛；
- 相对 incumbent 的 Sharpe/回撤退化容忍度；
- 输入数据完整性和最新日期。

结果处理：

- challenger 通过绝对门且不劣于 incumbent：发布 challenger。
- incumbent 通过绝对门、challenger 未显著改善：参数不变，仅续期验证证据。
- 两者均失败：状态设为 `rejected`，不发布参数。
- 有效样本不足：状态设为 `insufficient_evidence`，不把未知误判为通过。

## 6. 运行时失败关闭

新增统一的 MR 生命周期状态读取函数，供引擎、API 和审计复用。

信号处理顺序必须保持：

1. CRASH 禁入；
2. 已持仓止损；
3. 正常卖出、减仓和弱势退出；
4. 仅在准备返回 `buy` 时检查当前 Regime 生命周期；
5. 生命周期不可用时将潜在买入转换为 `no_entry`，并返回机器可读原因。

该顺序确保过期参数不会建立新风险，但不会阻止风险退出。

## 7. 单一来源与接口

- 生产引擎继续只从 `strategy_runtime.json` 读取参数。
- 策略健康审计改为读取 MR 生命周期和验证产物，不再用 `mr_optimization_results.json` 的生成时间代表生产参数年龄。
- 参数 API 返回 MR 参数、生命周期、验证数据截止日和当前是否允许新增仓。
- 回测页面的 MR 默认值和三态预设从参数 API 初始化；服务端不可用时才使用明确标记的只读 fallback。
- 旧 JSON 优化结果保留为历史证据，不再作为生产真相源。

## 8. 发布与回滚

- 发布仍使用现有原子写入、revision 递增和 `.bak` 备份机制。
- 验证运行必须有稳定 `run_id`，重复发布同一运行保持幂等。
- 参数变更和“仅续期验证”都记录 `published_by`、`validation_run_id` 和差异摘要。
- 任一写入、验证或序列化失败时，原生产配置保持不变。

## 9. 测试策略

实施采用测试驱动：

1. 生命周期校验：缺失、过期、拒绝和证据不足均失败关闭。
2. 信号顺序：过期参数阻止买入，但不阻止止损、卖出和减仓。
3. 发布合同：未附带新鲜样本外证据的 MR CI 结果不能刷新生命周期。
4. 续期合同：incumbent 通过而 challenger 无改善时，参数值不变、revision 和验证证据正确更新。
5. 审计合同：MR 年龄来自生产生命周期，不受旧优化文件时间影响。
6. API 合同：后端、前端预设与生产参数一致。
7. 回归验证：MR 专项、策略运行时、审计、生产门禁和完整非集成测试。

## 10. 非目标

- 不降低现有质量门以强行获得 ACCEPT。
- 不根据单次近期行情手工挑选参数。
- 不修改其他策略的参数生命周期。
- 不删除旧优化结果或历史备份。
- 不自动推送或部署。

## 11. 完成标准

- 不再存在通过修改日期即可让 MR 参数变“新鲜”的路径。
- 当前 Regime 的参数状态有可追溯样本外证据。
- 过期或验证失败时没有新买入信号，但退出路径保持工作。
- 审计、生产引擎、API 和前端显示同一组参数及生命周期状态。
- 所有专项及全量验证通过，工作树无意外改动。
